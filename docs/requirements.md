# 要求仕様書

## 1. 目的・範囲

Mobingoは、開催者と参加者が同じWebアプリを使用し、端末間通信なしでビンゴを進行・照合する静的PWAである。初回取得とアプリ更新には通信を要するが、キャッシュ完了後のゲーム進行はオフラインで可能である。サーバー、ユーザーアカウント、イベントのネットワーク同期は設けない。

本書は`req.md`と現行自作ソースを起点に要求を再構成したものである。実装確認は試験合格を意味しない。実測と差異は[設計テスト監査](design_test_audit.md)で管理する。

## 2. 利用者と利用条件

参加者はカードを作成して司会の出目に合わせて穴を開け、開催者は抽選と当選照合を行う。モードAは受付済み参加者を自動集計する少人数向け、モードBは事前受付を省略する運用である。想定人数はモードAが50人程度、モードBが100人以上であるが、性能保証値ではない。

Web CryptoとService Workerの利用にはHTTPSまたはlocalhostを必要とする。カメラには権限を要する。カメラ拒否時も4文字IDの手入力で進行できる。音声、振動、Wake Lockの非対応はゲーム判定を妨げない。

## 3. 機能要求と受入条件

| ID | 要求 | 受入条件 |
| --- | --- | --- |
| R-01 | 役割を選択できること | 参加者と開催者を選択し、確認付きで役割選択へ戻れること |
| R-02 | 4文字IDを扱えること | Crockford Base32の32文字、O→0・I/L→1、小文字補正、空白・ハイフン除去、最大4文字、生成IDの妥当性を満たすこと |
| R-03 | 端末によらず生成結果が一致すること | 同じID・用途で同じ鍵と配列を得て、親と子の用途を分離すること。既存v1の生成結果を維持すること |
| R-04 | 標準カードを作成できること | 5×5、各列の15数字範囲、24数字の重複なし、中央FREE常時開封であること |
| R-05 | 誤操作に強い穴あけができること | 400ms未満のタップで開封、開封済みは600ms以上で復元、移動・キャンセルで状態変更しないこと。FREEを復元しないこと |
| R-06 | リーチとビンゴを表示できること | 横5・縦5・斜め2の12ラインを判定し、待ち数字を重複なく昇順表示すること。複数リーチとビンゴの表示・演出を切り替えること |
| R-07 | 75球を安全に抽選できること | 1〜75を重複なく排出し、スライド開始、回転・排出スキップ、二重排出防止、75手で停止すること |
| R-08 | 進行を確認・修正できること | 最新球、履歴最大20球、1〜75ボードを表示し、確認付きUndo・リセットで保存状態と表示が一致すること |
| R-09 | モードAで受付・集計できること | QR/手入力の受付、重複排除、削除、0人開始禁止、リーチ総数・ビンゴ成立者ID・次球の予告・一致数の少ない順の上位3件を表示すること |
| R-10 | モードBおよび共通の当選照合ができること | QR/手入力からカードを再現し、出目一致数、最初の成立手番・同手番の成立役、有効/未達成を表示すること |
| R-11 | 3種類の特殊役を解禁できること | 四隅4マス、X形9マス、十字9マス（中央FREEを含む）を扱うこと。自然成立が解禁前でも有効手番は解禁手番以降とすること |
| R-12 | ゲームを再開できること | ゲーム開始後の参加者ID・開封・特殊役、開催者ID・モード・手番・解禁手番・受付一覧、選択役割を保存し、再読込で復元すること。不正データをDOMへ流さないこと |
| R-13 | オフラインで再訪できること | 全実行資産を同一配信元からキャッシュし、通信遮断後の再読込で役割選択・カード・抽選が動作すること。他アプリのキャッシュを削除しないこと |
| R-14 | 縦横画面と投影表示を利用できること | スマートフォン縦画面でカードと主要操作が収まり、横画面ではサイド情報、開催者では出目ボードが見えること。投影画面を開閉できること |
| R-15 | 端末機能とライセンス表示を扱えること | ミュート、音声、振動、Wake Lockを機能検出し、情報モーダルと商標・同梱ライブラリ表記を表示すること |
| R-16 | 遅延処理が現在の画面だけに作用すること | モード変更・リセット・モーダル終了後に旧タイマー、鍵導出、カメラ取得が保存・表示を変更しないこと。ストリーム、RAF、ResizeObserverを解放すること |

## 4. 非機能要求

- 決定論的生成はPBKDF2-SHA256（30,000回、256bit）とChaCha20、棄却法による一様整数とFisher–Yatesを用いる。描画演出の`Math.random`は判定に使わない。
- IDは20bit、計1,048,576通りであり、秘密情報や本人認証ではない。同じIDなら同じカードとなる。衝突、IDの共有、端末改変、開催シード既知時の先読みを完全には防止しない。
- 保存データ、手入力、QRは外部入力である。型・長さ・範囲を検査し、不正値でHTMLを構成しない。保存拒否時にもゲームのメモリ状態を継続できること。
- フロントエンドの資産だけで動作し、外部CDNを実行時に利用しない。実行用ビルドは不要である。開発用npmスクリプトと配信用静的資産を区別する。
- 4層テストと独立レビュー、各自作ファイルのLine/Branch 97%以上を[開発プロセス](development_process.md)の受入基準とする。

## 5. 原案からの移行判断

`req.md`は履歴資料として保持する。「通信を一切使用しない」はゲーム中の端末間通信不要と初回取得後のオフライン動作に限定する。「不正耐性完全」「KDFで探索チートを封殺」「10〜20ms」の保証は20bit IDと端末差から成立しないため採用しない。

Base32では0と1を許容する。X形と十字はFREEを含め9マス、実数字8個である。特殊役の有効成立手番は`max(自然成立手番, 解禁手番)`であり、解禁前成立カードの永久失格とはしない。投影は現在の出目の表示であり、別端末への配信ではない。

今後生成方式を変える場合はv1カード・出目との互換性を明示し、保存データの移行を別途設計する。今回の初期テスト整備では生成方式を変更しない。

モードAの受付一覧はゲーム開始時に保存する。受付中のブラウザ終了からの復元は原案の逐次保存要求からの未対応事項として明示し、今回の受入範囲は開始後の復元とする。受付途中の復元には受付フェーズを表す保存スキーマの追加設計を要する。
