# 要求仕様書

## 1. 目的・範囲

Mobingoは、開催者と参加者が同じWebアプリを使用し、端末間通信なしでビンゴを進行・照合する静的PWAである。初回取得とアプリ更新には通信を要するが、キャッシュ完了後のゲーム進行はオフラインで可能である。サーバー、ユーザーアカウント、イベントのネットワーク同期は設けない。

本書は`req.md`と現行自作ソースを起点に要求を再構成したものである。実装確認は試験合格を意味しない。実測と差異は[設計テスト監査](design_test_audit.md)で管理する。

## 2. 利用者と利用条件

参加者はカードを作成して司会の出目に合わせて穴を開け、開催者は抽選と当選照合を行う。モードAは受付済み参加者を自動集計する少人数向け、モードBは事前受付を省略する運用である。想定人数はモードAが50人程度、モードBが100人以上であるが、性能保証値ではない。

Web CryptoとService Workerの利用にはHTTPSまたはlocalhostを必要とする。カメラには権限を要する。カメラ拒否時も4文字IDの手入力で進行できる。音声、振動、Wake Lockの非対応はゲーム判定を妨げない。

| R-14 | 縦横画面と投影表示を利用できること | スマートフォン縦画面でカードと主要操作が収まり、横画面ではサイド情報、開催者では出目ボードが見えること。開始・参加・開催者セットアップ、受付、カード、全モーダル、投影を縦横で操作できること。縦向き投影では75数字を15数字×5行で表示し、投影・戻る操作を右上へ集約すること。スマートフォンの樽を縦200px以上・横160px以上で表示すること |

| R-16 | 遅延処理が現在の画面だけに作用すること | モード変更・リセット・モーダル終了後に旧タイマー、鍵導出、カメラ取得が保存・表示を変更しないこと。ストリーム、RAF、ResizeObserverを解放すること |

## 4. 非機能要求

- 決定論的生成はPBKDF2-SHA256（30,000回、256bit）とChaCha20、棄却法による一様整数とFisher–Yatesを用いる。描画演出の`Math.random`は判定に使わない。
- IDは20bit、計1,048,576通りであり、秘密情報や本人認証ではない。同じIDなら同じカードとなる。衝突、IDの共有、端末改変、開催シード既知時の先読みを完全には防止しない。
- 保存データ、手入力、QRは外部入力である。型・長さ・範囲を検査し、不正値でHTMLを構成しない。保存拒否時にもゲームのメモリ状態を継続できること。
- フロントエンドの資産だけで動作し、外部CDNを実行時に利用しない。実行用ビルドは不要である。開発用npmスクリプトと配信用静的資産を区別する。
- 4層テストと独立レビュー、各自作ファイルのLine/Branch 97%以上を[開発プロセス](development_process.md)の受入基準とする。

## 5. 原案からの移行判断

`req.md`は履歴資料として保持する。「通信を一切使用しない」はゲーム中の端末間通信不要と初回取得後のオフライン動作に限定する。「不正耐性完全」「KDFで探索チートを封殺」「10〜20ms」の保証は20bit IDと端末差から成立しないため採用しない。

Base32では0と1を許容する。X形と十字はFREEを含め9マス、実数字8個である。特殊役の有効成立手番は`max(自然成立手番, 解禁手番)`であり、解禁前成立カードの永久失格とはしない。投影は現在の出目の表示であり、別端末への配信ではない。

今後生成方式を変える場合はv1カード・出目との互換性を明示し、保存データの移行を別途設計する。今回の初期テスト整備では生成方式を変更しない。

モードAの受付一覧はゲーム開始時に保存する。受付中のブラウザ終了からの復元は原案の逐次保存要求からの未対応事項として明示し、今回の受入範囲は開始後の復元とする。受付途中の復元には受付フェーズを表す保存スキーマの追加設計を要する。

## 6. 表示名・当選順・PC/タブレット表示の追加要求

| ID | 要求 | 受入条件 |
| --- | --- | --- |
| R-17 | 表示名を設定してQRで渡せること | 任意の表示名を作成時・参加後に設定でき、再読込で保持する。32コードポイント以下、空白除去・NFC正規化を行い、制御文字を拒否する。QRから開催者が取得できる。IDとカード・出目の生成結果は変わらない |
| R-18 | 成立手番順の当選一覧を見られること | モードAの登録者と、各モードで有効と照合済みのカードを対象に、最初の成立手番順・同手番は同順位で表示する。表示名とIDを併記し、重複登録、Undo、解禁、復元、新ゲームで整合性を維持する |
| R-19 | PC/タブレットを含む表示を整えること | 非正方形セルでも復元リングが欠けない。開催者は4:3・正方形・縦長・横長で幅を使い、参加者は適切なカード幅を保つ。スマホ縦のID/リーチは1行で、表示されるリセットは1個の小型ボタンとする。QRは大きな操作を維持する |

表示名は自己申告であり認証情報ではない。HTMLとして解釈せず、入力・QR・保存復元のすべてを不信な入力として検証する。同名でもIDが異なれば別カード、同じIDは1カードである。自動的なネットワーク共有は行わず、名前の変更は新しいQRを読み取った開催者へ反映する。

| ID | 要求 | 受入条件 |
| --- | --- | --- |
| R-20 | アプリの文章を「ですます」調に統一すること | 当選順の説明・空状態と全自作画面の文章を点検する。説明、確認文、エラーは丁寧体とし、ボタン・見出し等の短い操作名や名詞ラベルは維持する。文書本文の「である」調とは区別する |

## 8. スマートフォンの操作とフィードバック（R-22）

音声はタッチ終了を含む利用者操作で初期化・再開し、中断後にも再試行する。穴あけ、復元、樽回し、球排出に振動を付け、音声と独立したオン・オフを保存する。端末非対応・拒否時も操作を継続できること。実際の音声・振動は実機確認の対象である。

通常回転は2.3秒とする。球表示中のタップは表示終了のみ、成立したスライドは表示終了と次球の回転開始を行う。75球目の表示を終了しても76球目を開始しない。表示終了・次球開始・自動終了で開催者パネルのスクロール位置を維持する。

参加者のQRボタンは「参加登録・照合用QR」の用途を明記する。縦横とも再作成操作の上に区切り線と余白を置く。

両役割のリセットは原則2回確認し、どちらの確認で取り消してもデータを変更しない。参加者は現在のカードがビンゴ成立中の場合、開催者は75球排出済みまたはモードAで1人以上の登録者全員がビンゴ成立中の場合に1回とする。モードBでは参加者全員を把握できないため全員成立の省略条件を適用しない。球表示中はその球を含む手番で判定する。

## 9. アプリURLの共有（R-23）

共通ヘッダーのURL共有ボタンから、URLのコピー、端末の共有メニュー、URL共有用QRコードを選べること。共有対象は現在開いているアプリのoriginとpathnameであり、queryとhashを除去する。カードID・表示名・出目などのゲーム状態をURLへ追加しない。

URLは選択可能な欄にも表示する。コピー権限拒否・非対応では選択と手動コピーへ案内し、共有メニュー非対応ではコピーとQRを利用できること。送信先の選択は利用者が端末の共有メニューで行う。共有の取消と失敗を区別し、Promiseの成功を相手への配送完了と断定しない。参加登録・当選照合のQRとは用途を区別する。

非同期処理の連打を抑止し、閉鎖・役割変更・再表示後に旧DOMを書き換えない。QRは同梱ライブラリで生成し、オフライン再訪でも使用できること。320px幅の開催者ヘッダーと低い横画面でも、共有操作・URL・QR・閉じるへ到達できること。実端末の共有先への配送は実機確認の対象である。

## 10. 音声・振動の実機切り分け（R-24）

Pixel 9aで音声・振動がともに反応しない報告に対応し、アプリ情報に「音を試す」「振動を試す」を設ける。アプリ設定を尊重し、ミュート・振動オフ、API非対応、明示的な拒否・例外、音声の開始待ち、ブラウザーによる要求受付を区別する。APIの成功を実際の発音・振動の成功と表示しない。

音声の再開を利用者操作から要求し、完了前に確認音を予約しない。2秒以内に完了を確認できなければ開始待ちとし、閉鎖・時間切れ後の遅延完了で音を鳴らさない。振動確認は利用者操作内で200msを要求し、戻り値falseを拒否として表示する。確認操作でゲーム状態とオン・オフ設定を変更しない。

確認情報は実行版、ブラウザー、起動形態、利用者操作の有無、API対応・設定・音声状態・直近の振動要求結果を端末内に表示する。ゲームIDや個人名は収集せず、自動送信しない。端末のメディア音量、消音・集中モード、振動設定、音声出力先など、Web APIから確認できない状態は利用者の実機確認と区別する。
