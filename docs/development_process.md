# 開発プロセス定義書

## 1. 目的と適用範囲

本書はMobingoの機能追加、仕様変更、不具合修正および保守に適用する開発手順と品質ゲートの定義である。対象は静的HTML・CSS・ES Modules、Service Worker、ローカル同梱ライブラリおよび開発用ツールである。バックエンド、会計処理、外部認証、暗号化DBは本システムの構成要素ではない。

ユーザーの明示的な指示を本書より優先する。今回の初期整備は、プロセス定義書と設計書までをmainに段階別コミットし、テスト追加以降を作業ブランチで実施する例外である。外部へのpush、PR公開およびmainへのコード統合は別の操作である。

## 2. 基本方針

1. 全体の状態遷移、データフロー、入力境界、オフライン動作を確認してから変更する。
2. 要求と設計を先に定義し、実装との差異を隠さず記録する。現状の不具合を正しい仕様として追認しない。
3. 実装前に再現・回帰テストを作成する。失敗原因をテスト、実行環境、製品に切り分ける。
4. 設計、テスト設計・実装、最終コードの各段階で、実装担当とは別の独立サブエージェントによるレビューを必須とする。
5. 通常はmainから`feature/*`、`fix/*`、`test/*`、`docs/*`を作成し、PR経由で統合する。ユーザー承認済みの初期文書整備は第1章の例外に従う。
6. レビューやテストで指摘が生じた場合、影響する最上流工程から設計、テスト、実装、レビューを再実行する。
7. コミットは工程単位に分け、英語のConventional Commitsを用いる。失敗再現用テストのコミットは失敗理由を記録し、受入合格とは区別する。

## 3. 文書体系

| 文書 | 責務 |
| --- | --- |
| [要求仕様書](requirements.md) | 利用目的、機能・非機能要件、受入条件、原案からの移行判断 |
| [外部設計書](external_design.md) | 利用者に見える挙動、入力、出力、保存・復元の契約 |
| [内部設計書](internal_design.md) | モジュール、乱数生成、判定アルゴリズム、状態、非同期処理 |
| [UI設計書](ui_design.md) | 画面構成、操作、表示状態、レスポンシブ表示 |
| [設計テスト監査](design_test_audit.md) | 要求ID、設計ID、具体的assert、テスト層、環境および未検証事項 |
| `docs/reviews/review<連番>.md` | 独立レビューの対象、指摘、対応、再レビュー結果、残余リスク |

`req.md`は取り込み前の原案として保持する。以降の規範は本書と上記4文書である。

## 4. 開発手順

### Phase 1：要求・設計

要求、全自作ソース、既存テストを確認し、変更の影響を4文書と設計テスト監査へ反映する。未実装・既存不具合・実機依存は区別する。保存形式と決定論的生成結果は不用意に変更しない。

### Phase 2：独立設計レビュー

独立サブエージェントが要求との整合性、状態遷移、保存データ、QR入力、XSS、資源解放、オフライン動作を精査する。指摘はPhase 1に戻して是正し、再レビューする。対象と証拠を`docs/reviews/`に保存する。

### Phase 3：4層テストと独立テストレビュー

| 層 | 配置 | 主な検証対象 |
| --- | --- | --- |
| 単体 | `test/unit/` | Base32、KDF、ChaCha20、カード、ライン、境界値 |
| 結合 | `test/integration/` | 生成と検証、保存と復元、ブラウザAPI境界、SWとキャッシュ |
| システム | `test/system/` | 開始から終了・復元までの業務シナリオ、モードA/B、オフライン再訪 |
| UI | `test/ui/` | Chromiumの実DOM、クリック、入力、pointer操作、モーダル、縦横画面 |

正常系だけでなく不正入力、キャンセル、移動、連打、非同期完了後の画面遷移、保存失敗を含める。UIは実ブラウザで実行し、実DOMの状態と保存結果をassertする。テストの存在や名称を網羅の根拠としてはならない。

独立サブエージェントが期待値の妥当性、独立した計算根拠、欠落ケース、テストの不安定性をレビューする。製品不具合が検出された場合は失敗証拠を保存し、テスト自体の妥当性を確立してから修正する。

### Phase 4：実装と静的検査

必要な設計更新と失敗テストを先行させてから製品を修正する。類似箇所も横断確認し、不要コードを削除する。保存済みカードと出目の再現性を維持する。

検査コマンドはテスト基盤の追加時に整備する。未整備のコマンドを実行済みとは扱わない。

- `npm run check:syntax`：自作JSの構文、JSONの構文を検査する。未定義変数の検出やMermaid検査とは別である。
- `npm run check:types`：TypeScriptの`allowJs`・`checkJs`による自作JSの型検査を行う。
- `npm run lint:indent`：コードのタブインデントを検査する。
- `npm run lint`：上記の静的検査をまとめて実行する。

コードのインデントはタブ、表示幅4である。Markdown本文、同梱外部ライブラリ、生成物とlockfileはインデント検査対象外である。ブロックコメントの` *`継続行は許容する。文書は「である」調、応答は「ですます」調である。

製品変更ではSemVerを更新する。互換性を壊す変更はMajor、互換性のある機能追加はMinor、不具合修正はPatchである。現構成の管理対象は`package.json`、`package-lock.json`のルートパッケージ情報、`sw.js`の`mobingo-vX.Y.Z`キャッシュ名である。存在しない`version.json`やバージョン表示要素を前提にしない。文書・テストのみのコミットでは製品バージョンを変更しない。

### Phase 5：最終レビューと受入

以下をすべて満たすまで最終受入合格とはしない。

- 静的検査のエラーが0件である。
- 単体、結合、システム、UIの全テストが合格する。
- 自作の`js/`以下と`sw.js`の各ファイルでLineとBranchがそれぞれ97%以上である。外部ライブラリ`js/lib/`、テスト、開発用スクリプトは測定対象外である。未ロードの対象も0%として扱い、集計値でファイルごとの不足を隠さない。
- 独立サブエージェントによる実装後コードレビューで未解決指摘が0件である。
- 要求とassertの対応、実行コマンド、実測件数、測定対象、残余リスクが記録されている。

NodeとChromiumで測ったカバレッジは対象と環境を明記する。合算する場合はソース位置の対応を保ち、別集計の場合は同じ指標として扱わない。実機カメラ、振動、音声、スリープ防止、配信HTTPSと端末固有のPWA更新はローカル自動試験だけでは証明できない。

### Phase 6：コミット・PR・統合

工程ごとに差分と検証結果を確認して英語でコミットする。PR草案は日本語で、背景、変更内容、確認内容、テスト結果、レビュー結果を含める。実測結果と未達ゲートを明記する。push、PR公開、マージの実施有無を正確に記録する。

## 5. 不具合是正と再入場

1. 再現操作、期待値、実結果、原因分類を記録する。
2. 同じ原因が他画面、保存復元、非同期処理、SWにないか調査する。
3. 要求・設計に問題があればPhase 1、テスト不足ならPhase 3へ戻る。
4. 再現テストを先に追加し、修正前の失敗と修正後の成功を記録する。
5. 関連する静的検査と4層全テストを再実行し、独立再レビューを受ける。
6. 完了後やPR準備後の発覚でも同じ手順を適用する。

## 6. レビュワーへの指示

レビュー依頼には対象ファイル、工程、要求ID、実行結果を示す。お世辞、挨拶、要約、点数、図は出力しない。指摘がない場合の応答は`PASS`のみとし、指摘がある場合は`<ファイル>:<行番号>: <理由と修正対象>`を箇条書きにする。

設計・実装・テストの不足、存在しない識別子、誤ったDOM参照、入力境界、保存形式、乱数互換性、カメラやタイマー等の資源解放を確認する。レビューのPASSとカバレッジ等の機械的ゲートの合否は別々に記録する。Mermaidを追加する場合は専用パーサーで検証し、JS構文検査で代用しない。
